# Phase 3 Delta — Production Readiness Fixes

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Fix 4 remaining production-readiness issues after auditing the (mostly pre-implemented) Phase 3 work: rate limiter ordering bug, missing request-scoped logger, missing frontend Sentry, and docker-compose env gaps.

**Architecture:** Backend middleware ordering is incorrect — auth/upload rate limiters are mounted *after* their routes and will never fire. A lightweight request-logger middleware is needed to attach `req.id` to pino log lines. Frontend needs `@sentry/react` for client-side error monitoring. Docker compose needs `SENTRY_DSN` and a root `.env.example` for required secrets.

**Tech Stack:** express-rate-limit, pino, @sentry/react, Docker Compose

**Pre-read:** `docs/superpowers/plans/2026-07-09-production-readiness-phase3.md` (the full plan — this delta only covers what's actually broken or missing)

### Task 1: Fix rate limiter ordering bug

**Issue:** In `hirehub-api/src/app/app.ts`, all three rate limiters (`generalLimiter`, `authLimiter`, `uploadLimiter`) are mounted *after* their corresponding route handlers via `app.use()`. Express will never invoke a middleware mounted after the route that already handled the request. This means `authLimiter` (lines 52-55), `uploadLimiter` (line 63), and `generalLimiter` (line 68) are all dead code.

**Files:**
- Modify: `hirehub-api/src/app/app.ts`

- [ ] **Step 1: Read current app.ts middleware ordering**

```bash
cat -n hirehub-api/src/app/app.ts | head -75
```

Confirm the ordering bug: authRoutes mounted at line 51, authLimiter applied at lines 52-55.

- [ ] **Step 2: Move `generalLimiter` to the top of the middleware stack**

`generalLimiter` should be the first middleware after `cookieParser()` and `express.json()` — before any route registrations. It provides a baseline rate limit for every request. Change lines 32/33 to insert it:

Old:
```ts
app.use(requestId)
app.use(express.json({ limit: '1mb' }))
```

New:
```ts
app.use(requestId)
app.use(express.json({ limit: '1mb' }))
app.use(generalLimiter)
```

- [ ] **Step 3: Remove the orphan `app.use(generalLimiter)` at line 68**

Delete the line:
```ts
app.use(generalLimiter)
```

- [ ] **Step 4: Move `authLimiter` before `authRoutes`**

Old:
```ts
app.use('/api', authRoutes)
app.use('/api/auth/login', authLimiter)
app.use('/api/auth/register', authLimiter)
app.use('/api/auth/forgot-password', authLimiter)
app.use('/api/auth/reset-password', authLimiter)
```

New (apply authLimiter as a blanket on the entire `/api/auth` path before mounting the router):
```ts
app.use('/api/auth/login', authLimiter)
app.use('/api/auth/register', authLimiter)
app.use('/api/auth/forgot-password', authLimiter)
app.use('/api/auth/reset-password', authLimiter)
app.use('/api', authRoutes)
```

- [ ] **Step 5: Move `uploadLimiter` before `uploadRoutes`**

Old:
```ts
app.use('/api', uploadRoutes)
app.use('/api/upload', uploadLimiter)
```

New:
```ts
app.use('/api/upload', uploadLimiter)
app.use('/api', uploadRoutes)
```

### Task 2: Add request-scoped logger middleware

**Issue:** `req.id` is generated by `request-id.ts` but never included in log output. All log lines from a request lack a correlation ID, making debugging in production harder.

**Files:**
- Create: `hirehub-api/src/middleware/request-logger.ts`
- Modify: `hirehub-api/src/app/app.ts` — register after `requestId`
- Modify: `hirehub-api/src/middleware/error-handler.ts` — use `req.log` or `req.id` in error logs

- [ ] **Step 1: Create `request-logger.ts`**

```ts
import type { Request, Response, NextFunction } from 'express'
import { logger } from '../config/logger'

export function requestLogger(req: Request, _res: Response, next: NextFunction) {
  req.log = logger.child({ reqId: req.id })
  next()
}

declare global {
  namespace Express {
    interface Request {
      log: typeof logger
    }
  }
}
```

- [ ] **Step 2: Register in `app.ts` after `requestId`**

```ts
import { requestLogger } from '../middleware/request-logger'
// ...
app.use(requestId)
app.use(requestLogger)
app.use(express.json({ limit: '1mb' }))
```

- [ ] **Step 3: Update `error-handler.ts` to use `req.log` when available**

In the two `logger.error(...)` calls (lines 59 and 64), replace with:

```ts
const log = _req.log || logger
```

Then use `log.error(...)` instead of `logger.error(...)` throughout. The Prisma default error at line 59 and the unhandled error at line 64 should use the request-scoped logger.

### Task 3: Add frontend Sentry error monitoring

**Issue:** Backend has `@sentry/node` integration but the frontend has no error monitoring. Crashes in the React app go unreported.

**Files:**
- Modify: `hirehub-frontend/package.json` — add `@sentry/react`
- Modify: `hirehub-frontend/src/main.tsx` — initialize Sentry
- Modify: `hirehub-frontend/src/App.tsx` — wrap in `Sentry.ErrorBoundary`

- [ ] **Step 1: Install `@sentry/react`**

```bash
cd hirehub-frontend && bun add @sentry/react
```

- [ ] **Step 2: Initialize Sentry in `main.tsx`**

Add before `createRoot(...)`:

```ts
import * as Sentry from '@sentry/react'

Sentry.init({
  dsn: import.meta.env.VITE_SENTRY_DSN,
  environment: import.meta.env.MODE,
  tracesSampleRate: import.meta.env.PROD ? 0.1 : 0,
  integrations: [Sentry.replayIntegration()],
  replaysSessionSampleRate: 0.1,
  replaysOnErrorSampleRate: 1.0,
})
```

The `dsn` is read from `VITE_SENTRY_DSN` env var (maps to `VITE_*` convention; Vite makes it available at build time). No DSN = no-op in dev.

- [ ] **Step 3: Wrap `<App />` in `Sentry.ErrorBoundary`**

In `main.tsx`, replace:
```tsx
<App />
```

With:
```tsx
<Sentry.ErrorBoundary fallback={<div className="min-h-screen flex items-center justify-center bg-canvas text-ink-muted">An unexpected error occurred.</div>}>
  <App />
</Sentry.ErrorBoundary>
```

- [ ] **Step 4: Add `VITE_SENTRY_DSN` to `.env.example`**

Append to `hirehub-frontend/.env.example`:
```

```

- [ ] **Step 5: Add `VITE_SENTRY_DSN` to the docker-compose frontend service**

(See Task 4 step 3)
